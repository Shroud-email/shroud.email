# Passkeys for account sign-in

## Purpose and scope

Give existing Shroud.email users a passwordless, phishing-resistant way to sign in. A confirmed, signed-in user can add and manage passkeys on Security settings, alongside the existing TOTP controls. On the login page, passkeys appear in browser autofill where supported, and a visible button offers a passkey picker otherwise. If the browser has no passkey, the password form continues to work unchanged. A verified passkey signs the user in directly, without a separate TOTP prompt. Password + TOTP, password reset, registration, and API token authentication remain available; this does not remove TOTP or create passwordless accounts.

## Library and boundaries

Use the Hex package `wax_` for WebAuthn registration and assertion validation, rather than implementing the protocol ourselves. `webauthn_components` wraps Wax but owns a LiveComponent-based ceremony, whereas this app's login and settings flows are controller-based; adopting it would add a second authentication UI architecture. The 2023 Shadowfacts article is explanatory, not production-ready, and its client-side checks are not a substitute for server verification.

The Accounts context owns passkey persistence and credential lookup/update. A separate passkey credential belongs to exactly one user, with a globally unique opaque credential ID, the public key in Wax's expected format, a stable opaque WebAuthn user handle, a display label and timestamps. Support multiple credentials per account; cascading account deletion removes them. User handles must not expose email addresses and must be checked against the credential's user at authentication. Store no private keys. Migrations create the credential and one-use challenge tables with their required uniqueness, expiry and foreign-key constraints.

Browser code in the existing `app.js` bundle handles WebAuthn binary encoding and `navigator.credentials.create/get`; it does not decide whether a response is valid. Controller endpoints issue options, verify responses and connect successful assertions to `UserAuth.log_in_user/2`, preserving its session renewal, confirmation redirect and return-to behavior. Keep the existing password login controller behavior and CAPTCHA limited to the password path; passkey verification is a separate authenticated protocol, not an alternative password submission to that action.

## Enrollment and management

On `/settings/security`, show a Passkeys section under the TOTP section, with an Add passkey action and a list of existing passkeys (name/creation date and Remove). Registration is available only to confirmed signed-in users. Require the current account password to authorize adding or removing a credential, so an unattended authenticated session alone cannot add an attacker's key or revoke the user's keys. Users retain the password fallback and can add multiple passkeys. Removal is scoped to the signed-in user's credential; removing the last passkey is permitted because password recovery remains. An unsupported browser or canceled ceremony leaves settings unchanged and displays a useful message.

The server generates a fresh, short-lived registration challenge tied to the current user and trusted site origin/RP ID. The browser asks for a *discoverable* credential (resident key required) with user verification required, without restricting registration to built-in authenticators: synced passkeys and PIN-protected roaming keys can both work. Send the current user's opaque handle, account email as display name, and existing credential IDs for exclusion. Wax verifies the attestation and signed client data on the server, including type, challenge, origin, RP ID and verification flags. Persist the credential ID and public key extracted from the **verified** attestation, not client-provided key material. Reject duplicates or a registration for a different user; consume the challenge whether verification succeeds or fails.

## Sign-in

On GET `/users/log_in`, keep the existing email/password form. Annotate the email field with `autocomplete="username webauthn"`. Where the browser supports conditional mediation, start `navigator.credentials.get({mediation: "conditional"})` with an empty/omitted allow-credentials list when the page loads. This does not open a modal or silently sign anyone in: it waits for the user to select a passkey in autofill. The visible Sign in with a passkey button starts a normal modal WebAuthn request with the same server-side verification. Abort the pending conditional request before opening the modal. On unsupported browsers, hide or disable passkey-only controls but retain password login; absence of a credential, cancellation, or an autofill promise that remains pending must not block the password form.

The server issues a fresh, short-lived, one-use authentication challenge independent of any email address. After the authenticator responds, find the credential by its opaque ID, verify the returned user handle belongs to the same user, then ask Wax to validate the assertion against that credential's stored key and the trusted challenge. Require the user-verification flag: device PIN, password, fingerprint or face unlock qualifies, but presence-only touch does not. Require the expected WebAuthn type, origin and RP ID, valid signature and challenge, and a still-existing credential/account. Record sign-counter information where available; synced passkeys may legitimately report zero, so do not treat zero as proof of cloning. Consume a challenge atomically on attempted verification to prevent replay and parallel reuse; challenge expiry and cleanup keep pending records bounded. Failed assertions return a generic sign-in error without revealing whether a user or credential exists and never establish a session. A successful assertion uses existing session login and bypasses the TOTP step; the password path still invokes TOTP when configured.

## Trust and failure handling

Derive the expected origin and RP ID from the **configured public endpoint**, not an untrusted `Host` or `Origin` request header. HTTPS is required outside localhost. In deployments behind a portal or reverse proxy, enrollment and sign-in must use the same stable public origin/RP ID, with explicit configuration if the canonical endpoint differs; credentials registered for one RP ID cannot be reused on another. Browser requests use the existing CSRF-protected browser session. Keep challenge state server-side (rather than trusting a reusable signed session cookie alone) so one-time consumption is enforced across requests and app instances. Bind registration challenges to the signed-in user; authentication challenges are anonymous. Bound response sizes and handle malformed base64, missing fields, expired challenges, duplicate credentials and Wax errors as normal failed ceremonies, not server errors. Do not log raw assertions, challenges, or credential keys. Rate-limit anonymous challenge issuance/failed verification to avoid database and cryptographic abuse; retain existing CAPTCHA behavior for password login.

## Verification

Test enrollment and multiple-key management, authorization of additions/removals, distinct users' credential ownership, and successful passkey login with TOTP enabled. Exercise wrong origin/RP ID, wrong or expired challenge, replay and concurrent consumption, a mismatched user handle, absent user verification, malformed data and revoked credentials; none may create a session. Confirm password + TOTP and CAPTCHA flows are unchanged. Add browser checks for conditional autofill, manual picker, cancellation/unsupported browser and password fallback, and inspect rendered login and Security settings states in a running app. Use Wax's documented WebAuthn fixtures/test helpers where possible; never stub out verification in the security-path tests.

## Out of scope

Passkey-only account registration, removal of passwords or TOTP, API passkey authentication, cross-origin/related-origin passkeys, recovery-policy changes, and automatic passkey enrollment after password sign-in.
