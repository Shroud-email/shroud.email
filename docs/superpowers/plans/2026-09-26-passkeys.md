# Passkeys Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Existing users can enroll multiple passkeys in Security settings and sign in via autofill or a button without a password or TOTP code.

**Architecture:** Wax verifies WebAuthn on the server, with credential and one-use challenge records in Postgres. Existing browser controllers issue options and verify responses, then delegate to existing `UserAuth` session establishment; app.js owns browser ceremonies.

**Tech Stack:** Phoenix 1.8, Ecto/Postgres, Wax (`wax_` 0.7), esbuild, WebAuthn, ExUnit, node:test.

**Spec:** `docs/superpowers/specs/2026-09-26-passkeys-design.md`

## Global Constraints

- Registration and login require discoverable credentials and user verification `"required"`; do not restrict authenticators to platform only.
- Use configured public endpoint origin/RP ID, never request headers; HTTPS outside localhost.
- Existing password + TOTP, recovery, registration, CAPTCHA, API tokens and confirmation routing stay unchanged.
- Challenges expire quickly (choose 5 minutes) and are consumed atomically once, even on failed verification; enrollment is account-bound.
- A signed-in confirmed user supplies their current password to add or remove a credential.
- Follow repository AGENTS.md; generate Ecto migrations via `mix ecto.gen.migration`.

## Review Focus

- A reused/parallel assertion must not authenticate twice: cover atomic challenge consumption in Task 2.
- A credential belonging to another user or a mismatched user handle must not authenticate: cover Task 4.
- A UV-absent but otherwise valid assertion must fail, even if Wax defaults to `"preferred"`: cover Task 4.
- A second manual get while conditional mediation is pending must abort the first request: cover Task 5.
- A canceled/unsupported WebAuthn request must preserve password login and leave credentials unchanged: cover Tasks 3 and 5.

### Task 2: Issue and consume one-use Wax challenges

**Files:** Create `lib/shroud/accounts/passkeys.ex`, `lib/shroud/accounts/passkey_challenge.ex`; generate `priv/repo/migrations/*_create_passkey_challenges.exs`; test `test/shroud/accounts/passkeys_test.exs`.

**Interfaces:** Produce `Passkeys.begin_registration(%User{}) :: {:ok, map()}`, `Passkeys.begin_authentication() :: {:ok, map()}`, `Passkeys.consume_challenge(binary(), :registration | :authentication, User.t() | nil) :: {:ok, Wax.Challenge.t()} | {:error, atom()}`. Public map contains encoded challenge token/bytes and RP ID, plus user handle/excluded credentials for registration. Keep Wax challenge state server-side and bind a random challenge token to the browser's CSRF-protected session; store only trusted serialized challenge data (never decode untrusted Erlang terms), expiry and optional user_id. Atomic delete-returning on consume, with kind/user/expiry predicates. If multiple browser gets issue challenges, token uniquely identifies the intended one; cleanup expired rows during issuance.
